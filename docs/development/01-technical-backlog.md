**BE-035 — Hallazgo propio de esta validación (`TEST-API-001`):** dos desviaciones reales entre `openapi.yaml` y la implementación, encontradas al validar respuestas reales contra el spec real (no una copia) con `swagger-request-validator-mockmvc`. (1) `ReminderResponse` serializaba `description`/`dueAt` como JSON `null` cuando el reminder no los tenía, pero `Reminder` en `openapi.yaml` los declara `type: string`/`type: string, format: date-time` sin `nullable: true` (a diferencia de `ReminderShare.revokedAt`, que sí lo declara) — corregido en el código (`@JsonInclude(JsonInclude.Include.NON_NULL)` en `ReminderResponse`), no relajando el contrato. (2) los tres endpoints paginados (`GET /reminders`, `GET /reminders/{id}/shares`, `GET /me/invitations`) usan `allOf: [PageMeta, {items/shares+invitations}]`; el validador rechazaba cada instancia real porque interpreta cada rama de `allOf` como un schema cerrado (sin fusionar propiedades), rechazando los campos de la rama hermana como "additionalProperties no permitido" — la implementación ya era exactamente la unión que el contrato pretende describir, así que aquí el defecto real estaba en la composición del schema, no en el código; corregido añadiendo `additionalProperties: true` explícito a `PageMeta` y a cada rama inline de `allOf` en `openapi.yaml` (no afloja ningún tipo/campo/`required` ya validado, solo corrige la interacción `allOf`+`additionalProperties` de esta librería).

**Nota sobre `AND-002`/`AND-003`, `WEB-002`/`WEB-003`, clientes OIDC de `INFRA-002` (login + reminders CRUD real, 2026-08-15):** Android SDK instalado por terminal (`cmdline-tools` + `sdkmanager`, sin Android Studio); Xcode/iOS quedó **bloqueado** — `/opt/homebrew` pertenece a otro usuario del Mac y `sudo` requiere una contraseña interactiva que este entorno no puede proveer, así que `brew install xcodes` no pudo ejecutarse (ver `03-milestone-1-gate.md`/reporte de cierre de esta sesión para el comando exacto pendiente). Se añadieron 3 clientes OIDC públicos con PKCE S256 a `infra/keycloak/realm-vida-cotidiana.json` (`android-app`, `ios-app`, `web-spa`) y se verificó el flujo Authorization Code + PKCE completo contra un Keycloak real (script headless, sin navegador) antes de escribir ningún código de cliente. Web: login PKCE real + CRUD de reminders verificado con un navegador headless real (Playwright, Chromium) haciendo clic a través de la UI real — encontró y corrigió un bug real (React StrictMode reintentaba el intercambio del authorization code, que es de un solo uso). Android: login (AppAuth-Android) + reminders (Retrofit/Hilt) compilan y empaquetan de verdad (`./gradlew clean assembleDebug`, `BUILD SUCCESSFUL`, APK real de ~36 MB), con el redirect de AppAuth verificado en el manifest ya mergeado del APK (`aapt dump xmltree`) — pero sin dispositivo/emulador conectado en este entorno, nadie tocó la UI real (`adb devices` no lista nada), declarado como `BLOCKED_BY_ENVIRONMENT`, no simulado. iOS (`IOS-002`/`IOS-003`) sigue `TODO`, bloqueado por lo mismo que `IOS-001`. `./mvnw clean test`: 108/108 siguen en verde tras añadir CORS al backend (necesario para que el navegador permitiera las llamadas de `web-spa`, `SecurityConfig` con `vida-cotidiana.cors.allowed-origins`, default `http://localhost:5173`).

**Nota explícita sobre `AND-006`/`WEB-006`/`INFRA-007` (reporte de errores, 2026-08-16):** Firebase Crashlytics y GlitchTip autoalojado son, en este momento, **error-tracking de desarrollo local únicamente** — GlitchTip corre en `docker-compose.yml` (infraestructura local, igual que Keycloak/Postgres, con el mismo comentario de "no producción" en el archivo) y Crashlytics reporta contra el mismo proyecto Firebase de desarrollo usado para `AND-005`. Ninguno de los dos está conectado todavía a un entorno real/`staging`/producción — eso depende de `INFRA-004` (servidor propio, todavía `TODO`). No confundir "verificado con evidencia real" (el pipeline funciona de extremo a extremo, tal como se probó) con "desplegado en un entorno real" (no lo está). Alcance de esta sesión fue deliberadamente acotado a estas dos integraciones — CI, auditoría de seguridad, y cualquier otra herramienta de observabilidad quedan fuera, en ese orden según lo acordado.

**TBD explícito (no resuelto en código, por instrucción directa de la tarea):** qué ocurre con `REMINDER`/`REMINDER_SHARE`/`INVITATION` propiedad de o compartidos por una cuenta purgada (`BE-027`) — ninguna decisión aprobada (`DEC-002`, `DEC-015`, `28-v1-decision-pack.md`) especifica si esos recordatorios deben transferirse, eliminarse o quedar huérfanos con `owner_user_id` apuntando a una cuenta `DELETED`. Inventar ese comportamiento violaría la regla fundamental de no inventar requerimientos de negocio (CLAUDE.md). `User.purge()` anonimiza únicamente la fila `USER`; no toca ninguna otra tabla. Requiere una decisión explícita del Product Owner antes de implementarse.
